Your agents’ task board, outside the repo.

brie keeps one markdown file per task in a folder beside your repos. Your orchestrator writes a brief, a worker agent does it and reports back, and Status tells you where it stands.

Install brie View on GitHub

A CLI, a terminal UI and an MCP server over the same plain files. Written in Rust, nothing to keep running.

How a task moves

A brief is the whole task for one worker. It has a contract: four statuses, one order, and nothing edited except the status line and the bottom of the file.

  1. 1.0

    Onboard a repo

    Run brie add once. Your .briefs/ and .prototype/ folders move into ~/.alter-store and come back as symlinks, so the briefs stay out of your commits and diffs. brie link points another worktree at the same store. brie also writes a short block into AGENTS.md or CLAUDE.md that tells agents how to use it, and lets Claude Code write to the store without a permission prompt.

  2. 2.0

    Write a brief

    The orchestrator runs brie new and fills in what to read, what to do and what not to do. Keep it under one screen. Temporary files go in a Scratch folder under .prototype/, so nothing lands in your tree.

  3. 3.0

    A worker does it

    The worker is any agent you start. It sets Status to working before it reads anything, does the job, appends a Report, and sets Status to done last. Status is the only signal the orchestrator trusts.

    • ○ todo
    • ◐ working
    • ● done
    • ✕ blocked
  4. 4.0

    Wait, check, accept

    brie wait blocks until a brief is done or blocked and exits 0, 2 or 1 on timeout, so a script can branch on it. brie status is the short call: counts, then only the briefs that aren’t done, however many exist. Check the report against the real diff, then accept.

A cockpit for you

Run brie with no arguments for a full-screen view of every project, brief and prototype. It watches the files, so it is always current.

Live
The list refreshes every second. A worker’s Status change shows as it happens, and a brief that turns done or blocked rings the bell.
Find
/ searches names and contents. status:working filters by status.
Edit
Briefs open in a built-in markdown editor that renders as you type, while they are still drafts (todo).
Serve
s serves a prototype from a brief’s Scratch folder. v lists what is running.

Agents get tools, not a shell

brie mcp speaks MCP over stdio. It is opt-in: nothing starts it unless you add it to your agent’s config.

Use "args": ["mcp", "--worker"] for a worker. It gets brief_status, brief_read, brief_set_status, brief_report, scratch_path, contract and the read-only memory tools. The tools enforce the contract: brief_set_status sets only the Status line and brief_report appends at the bottom, and every tool refuses a file outside the project’s briefs folder.

brief_new
Create a brief and its Scratch directory; returns both paths.
brief_status
One brief’s status, or counts and the briefs not done. Short.
brief_read
Read a brief, or part of it by heading.
brief_set_status
Set the Status line. The only line of a brief that changes in place.
brief_report
Append to the bottom, under one Report heading.
brief_wait
Wait for briefs to be done or blocked. Returns after a timeout; call again.
scratch_path
The Scratch directory of a brief; every temporary file goes there.
contract
The brief rules, whole or for one role.
servers, server_stop
Running prototype servers, and a way to stop them.
memory_*
View, zoom, date, since, status, add and sub for the project’s memory.

A log that never ends

Long projects outgrow any context window. brie memory keeps the whole history and hands an agent a view that stays the same size. It is opt-in: off until you run brie add --memory.

Every message is logged word for word, append only. A cheap model compresses the log into a tree of one-line summaries: each message becomes a line, two neighbours merge into one, and so on.

An agent sees a view of 64 to 128 KB that covers the whole history, fine near the end and coarse far back. When a line is too vague, it zooms into the two lines it was made from, down to the original message.

It is experimental: you bring the summarizer and the agent as shell commands, BRIE_SUMMARIZER and BRIE_AGENT. brie memory turn runs one turn, and brie memory sub starts a subagent in the background.

Add brie to your workflow

One binary, no service to run. Then tell your orchestrator to use brie new.

Get the binary

Download brie-macos-arm64.tar.gz (Apple silicon) or brie-linux-x86_64.tar.gz (Linux) from Releases, then put brie on your PATH.

tar -xzf brie-macos-arm64.tar.gz
mkdir -p ~/.local/bin && mv brie ~/.local/bin/

Prefer source? cargo build --release after brew install rustup && rustup default stable.

Onboard your repo

From the repo root. Run it again any time; it changes nothing when the links are right.

brie add

Good to know

  • Early days. This is version 0.1, for macOS and Linux.
  • One machine at a time. brie sync backs the store up to a git remote. It is not a team tool.
  • brie doesn’t start agents. It is the protocol and the viewer, so it works with whatever runs your agents.
  • Status is a convention. The MCP tools enforce the contract; a worker that edits the file by hand can still break it.
